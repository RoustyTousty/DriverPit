## 0. New findings

### 0.1 A rematch runs with **no liveness heartbeat at all** — HIGH — reopens §3.3 — ✅ FIXED 2026-07-29

> **Resolution.** Fixed by lifting, as the finding's own "fix shape" recommends — the match id now has
> exactly one owner. `useDuelLifecycle` no longer copies `match` into state
> (`const [activeMatch, setActiveMatch] = useState(match)` → `const activeMatch = match`); it reads the
> prop and reports a rematch's new id **up** through a new `onMatchIdChange` callback, threaded through
> `DuelMatch`. `DuelRoot.handleMatchIdChange` applies it to the `match` it already owns, so all three
> consequences close at once: `heartbeatMatchId` re-arms on the new id (having correctly stood down on
> the old match going terminal), `setLiveMatchId` publishes the live rematch so a mid-rematch sign-out
> forfeits it, and `declareOpponentForfeit` is back to needing the server's second opinion. It also
> clears `initialRound`, which described round 0 of the *previous* match.
>
> Nothing keys on the id in two places any more, so this cannot silently recur; CLAUDE.md's "Exit,
> forfeit & disconnect" now states the single-owner rule.
>
> **Regression test:** `serverAuthoritativeWrites.test.ts` → *"follows the same players into a rematch,
> lobby phase included"* (DB tier). It pins the server contract the client has to satisfy: beating the
> old id contributes nothing, an un-beaten rematch row goes stale and forfeitable within one grace
> window, and a beat is accepted while the rematch is still `lobby` — which matters because staging +
> countdown (2 500 + 3 900 ms) sit inside `DISCONNECT_GRACE_MS`. Stated honestly: *which* id the browser
> beats is a component-level fact and there is still no component tier (§2.6), so the DB test brackets
> the bug rather than reproducing it. The finding's literal suggestion — "wait past the grace window
> without beating, assert the forfeit is refused" — would fail after the fix too, since a genuinely
> stale player *is* forfeitable by design; that is the contract, not the bug.
>
> `npx tsc --noEmit` clean; `npx vitest run` 167 passed, 114 skipped.

This is the most serious thing in this audit. Drizzle/0040's server-verified absence check — the
whole of §3.3's fix, the thing that stops "forfeit your opponent on demand" — is **inert for the
entire duration of every rematch.**

The heartbeat lives in `DuelRoot`, which was the right call
([DuelRoot.tsx:140-162](../components/duel/DuelRoot.tsx#L140-L162)):

```ts
const heartbeatMatchId = phase === "landing" || phase === "searching" ? null : (match?.matchId ?? null);
useEffect(() => {
  if (heartbeatMatchId === null) return;
  ...
  const beat = async () => {
    const result = await matchHeartbeat(heartbeatMatchId);
    if (!cancelled && result === "terminal") stop();
  };
  ...
}, [heartbeatMatchId]);
```

`match` is `DuelRoot`'s own state. A rematch never touches it. `DuelMatch` receives `match` as a
prop and hands it to `useDuelLifecycle`, which copies it into its **own** state and mutates the id
on rematch ([useDuelLifecycle.ts:481-498](../components/duel/useDuelLifecycle.ts#L481-L498)):

```ts
function transitionToRematch(newMatchId: number) {
  ...
  setActiveMatch((prev) => ({ ...prev, matchId: newMatchId }));
}
```

There is **no callback up to `DuelRoot`** — I grepped every prop `DuelMatch` accepts
([DuelMatch.tsx:23-53](../components/duel/DuelMatch.tsx#L23-L53)); there is no `onMatchChange`.
So `DuelRoot.match.matchId` stays pinned to the *old* match for the whole rematch, and three things
follow:

1. **`heartbeatMatchId` still names the old match.** `duel_heartbeat` returns `false` for a match
   whose `status` is `finished`/`abandoned`
   ([0040:64-72](../drizzle/0040_duel_match_liveness.sql#L64-L72)), which `matchHeartbeat` maps to
   `"terminal"` ([matchHeartbeat.ts:31](../lib/duel/matchHeartbeat.ts#L31)) — so the interval
   **stops itself the moment the first match finishes**, i.e. on the results screen, before the
   rematch even exists. `heartbeatMatchId` never changes afterwards, so the effect never re-arms.
   The new match gets **zero** heartbeats from either client.
2. **`duel_matches.last_seen_a/b` on the rematch row therefore never move.** They are
   `NOT NULL DEFAULT now()` ([0040:35-38](../drizzle/0040_duel_match_liveness.sql#L35-L38)), stamped
   when `requestRematch` inserts the row
   ([actions.ts:494-497](../lib/duel/actions.ts#L494-L497)). `DISCONNECT_GRACE_MS` is **10 000 ms**.
   Staging alone is `MATCH_FOUND_HOLD_MS` 2 500 + `COUNTDOWN_MS` 3 900, so **both players are
   "stale" roughly four seconds into round 1** and stay stale for the remaining ~3 minutes 55.
   `forfeitMatch(newMatchId, opponentId)` from a devtools console then passes
   [actions.ts:194-199](../lib/duel/actions.ts#L194-L199) against a fully present opponent: status
   `abandoned`, `winner_id = attacker`, real Elo written to the column the leaderboard sorts on.
   That is §3.3's exploit verbatim, and rematch is a **primary CTA on the results screen**, so it is
   not an obscure path.
3. **`setLiveMatchId` publishes the old id too**
   ([DuelRoot.tsx:123-127](../components/duel/DuelRoot.tsx#L123-L127)). Signing out mid-rematch
   calls `forfeitMatch(oldMatchId)`, which `duel_forfeit` no-ops on an already-terminal match — so
   the opponent is stranded for the grace window instead of getting the immediate clean win
   CLAUDE.md promises under "Signing out mid-match forfeits it". The sign-out confirmation still
   fires (`matchLive` is truthy), so nothing looks wrong.

The honest-path damage is the mirror image: `declareOpponentForfeit`'s retry loop
([useDuelLifecycle.ts:675-681](../components/duel/useDuelLifecycle.ts#L675-L681)) now *succeeds
first try* in a rematch, because the server-side second opinion §3.3 added has nothing behind it.
The four-layer story reverts to one client-side presence timer.

**Fix shape:** the match id has to be one value, not two. Either lift it into `DuelRoot`
(`onMatchIdChange` from `useDuelLifecycle`, or move `activeMatch` up), or move the heartbeat and
`setLiveMatchId` down into `useDuelLifecycle` where `activeMatch.matchId` already lives — the
latter loses the "covers staging onward" property that put the beat in `DuelRoot` in the first
place, so lifting is probably right. A regression test is available cheaply and belongs in
`serverAuthoritativeWrites.test.ts` rather than in a component test: *create a match, finish it,
create its rematch, wait past the grace window without beating, assert the opponent forfeit is
refused* — which fails today for the right reason.

### 0.2 `round_start` is payload-trusted on the intermission fast path — HIGH — extends §3.4 — ✅ DONE 2026-07-29

> **Resolution.** Closed twice over, which is what this finding asked for.
>
> The channel is private now (§3.4), so the payload can only come from the other participant at all.
> And the fast path no longer takes the clock from it: it keeps the branch — it is still the
> "opponent's ready-gate won the race" catch-up, and deleting it was never the answer — but calls
> `beginRound(matchId, nextRoundIndex)` and adopts *that* result
> ([useDuelLifecycle.ts:206-232](../components/duel/useDuelLifecycle.ts#L206-L232)). The broadcast
> now says only *that* a round started, never *when*.
>
> `beginRound` rather than the suggested `refreshRoundState()` on purpose. `refreshRoundState` goes
> through `getDuelRoundState`, a **Server Action** — a serverless invocation sitting between one
> round ending and the next starting, which is the exact latency drizzle/0034 moved this lifecycle
> off (and it is silently deducted from the countdown, since the clock is stamped when the RPC runs
> and the client only learns when the response lands). `duel_begin_round_client` is the warm
> one-hop RPC, it is already idempotent — the opponent's call stamped the round, so this one echoes
> the same `started_at`/`ends_at` back with `newly_started: false` — and it is the call this path
> was always going to make anyway, just triggered by their gate instead of mine. So the
> re-verification is a warm hop on a beat where the client is between rounds, not a cold one.
>
> A failed call is not a dead end: the intermission safety-net poll (`DUEL_POLL_INTERVAL_MS`) and
> this client's own ready-gate both still run. Racing with `proceedFromIntermission` is fine — both
> call the same idempotent RPC, and `adoptRound`'s `roundIndex <= roundIndexRef.current` guard makes
> the second a no-op.

§3.4 credits two handlers with re-verifying against authoritative state rather than trusting the
broadcast: *"`onForfeit` and `onRoundStart` **do** re-verify… `round_end` and `match_end` are the
two that don't."* The `onRoundStart` half of that credit is **only true in one of its two
branches** ([useDuelLifecycle.ts:176-208](../components/duel/useDuelLifecycle.ts#L176-L208)):

```ts
if (phase === "intermission" && intermission && !intermission.isLastRound
    && payload.roundIndex === intermission.nextRoundIndex) {
  adoptRound({ roundIndex: payload.roundIndex, startedAt: payload.startedAt, endsAt: payload.endsAt, ... });
  setIntermission(null);
  setPhase("playing");
  return;
}
void refreshRoundState();   // <- the branch that re-verifies
```

The fast path takes `startedAt` and `endsAt` **straight off the payload**. On an unauthenticated
channel (which `duel:{matchId}` still is — see §3.4 below, no `private: true`, no
`realtime.messages` policies anywhere in `drizzle/`) that hands an attacker the victim's round
clock:

- `endsAt` in the past → `useServerCountdown` reads 0 immediately, the round-expiry effect
  ([useDuelLifecycle.ts:608-614](../components/duel/useDuelLifecycle.ts#L608-L614)) fires
  `duel_close_round` at once, and the victim DNFs a round they never saw.
- `startedAt` far in the future → `isPreRound` stays true and the board never becomes live; the
  lights sequence sits there while the real server clock runs down.

Neither corrupts the database — `duel_submit_guess` validates the window server-side
([0022:199-208](../drizzle/0022_duel_submit_guess_rpc.sql#L199-L208)) — but both cost the victim the
round, which in a rated 1v1 is the point.

**This is a gap in the original finding, not a regression from §2.3's refactor.** I diffed the
handler against `git show 5b1a4aa:components/duel/DuelMatch.tsx` and it is character-identical; the
extraction moved it verbatim, as that resolution claims.

The real fix is §3.4's (`private: true` + `realtime.messages` RLS scoped to participants), which
closes this along with `round_end` and `match_end`. The cheap partial fix is one line: call
`refreshRoundState()` in the fast path too, and accept one extra round trip on a beat where the
client is already between rounds. Note the fast path exists for a reason — it is the "opponent's
ready-gate won the race" catch-up — so deleting it is not the answer.

### 0.4 `migrateLocalStats` silently truncates the guess distribution — LOW

[actions.ts:98-100](../lib/stats/actions.ts#L98-L100):

```ts
const mergedDistribution = current.guessDistribution.map(
  (count, i) => count + (clean.guessDistribution[i] ?? 0),
);
```

`.map` over `current` preserves **current's** length. `sanitizeLocalStats` produces a
`MAX_GUESSES`-length (6) array, so if the server row holds a 5-bucket distribution — which is
exactly what any `user_stats` row created between drizzle/0007 and drizzle/0016 holds, see §0.6 —
the legacy player's 6-guess wins are dropped on the floor and the row stays 5 buckets forever.

Narrow (legacy accounts only, one bucket, cosmetic in the Statistics chart) and safe in the
direction that matters — it can only lose counts, never invent them. `Array.from({ length:
MAX_GUESSES }, (_, i) => (current.guessDistribution[i] ?? 0) + (clean.guessDistribution[i] ?? 0))`
fixes it and normalises the row's length at the same time.

### 0.5 The `exhaustive-deps` suppressions grew from 12 to 17 — LOW — ✅ DECIDED + FIXED 2026-07-30

> **Resolution: ESLint is adopted, deliberately narrow, and the decision was made against the real
> numbers this finding asks for rather than against the feeling.**
>
> The finding's own instruction — *"recording it so the decision is made against the real number"* —
> is what shaped the method. Every candidate ruleset was **run over the tree first**, and only then
> chosen or rejected:
>
> | Candidate | Violations | Adopted? |
> |---|---|---|
> | `react-hooks/rules-of-hooks` | **0** | yes |
> | `react-hooks/exhaustive-deps` | **13**, every one already annotated | yes |
> | `@typescript-eslint/no-explicit-any` | **1**, already annotated | yes — it is CLAUDE.md's stated "No `any`" rule, enforced |
> | `@next/next` recommended | 1 real + 1 already annotated | yes, minus one rule (below) |
> | react-hooks v7 `recommended-latest` (the React Compiler preset) | **30** | **no** — see below |
>
> So the two classic hook rules **cost nothing to switch on**: the codebase already complies. That
> is the whole answer to "17 pre-existing violations to triage" — there were none to triage, because
> every genuine one already carried a reason at its call site. What switching the rule on bought is
> that those 13 comments are now *checked* claims instead of decoration.
>
> **The real number turned out to be 15, not 17, and 2 of those were lies.** The finding counted
> `eslint-disable` comments; 15 were `exhaustive-deps` and 2 were other rules. Running the rule for
> the first time showed only **13** of the 15 suppressed anything: `DuelIntermission.tsx:141` and
> `useDuelChannel.ts:285` suppressed nothing at all. Both are gone, each replaced by a plain comment
> saying why no suppression is needed. **That is a fact that could only be learned by running the
> rule**, and it is the clearest possible argument for the finding.
>
> **The ratchet.** `reportUnusedDisableDirectives` is set to **error**, so a suppression that stops
> being needed now fails the build. The finding's sharpest observation was that "the number moves in
> one direction on its own"; it now moves in the *other* direction on its own, and can only rise
> when someone writes a suppression deliberately.
>
> **What was deliberately not adopted, and why it matters more than what was.**
> `eslint-plugin-react-hooks` v7 ships a `recommended-latest` preset bundling the React Compiler
> diagnostics (`set-state-in-effect`, `purity`, `refs`, `immutability`). Measured: **30 violations**,
> and they land on patterns this codebase chose on purpose and documents — `GuessAnnouncer`'s entire
> design is state set from an effect (§4.1), `useLightsCountdown` reads `Date.now()` in render (§1.7,
> latent and accepted), `Modal`, `useServerCountdown` and `useCountUp` likewise. Adopting it would
> have meant **30 new suppressions on day one**, which is precisely the shape of the problem this
> finding is about. It is a separate decision, to be taken against its own numbers. Recorded in
> `eslint.config.mjs` so the next person doesn't re-derive it.
>
> **No style or formatting rules**, for the same reason `ci.yml` used to give for having no lint at
> all: `tsc --noEmit` is the type authority, this repo has never had a house style, and inventing one
> inside a lint adoption is how a lint step becomes something people skip. The rejected rule is
> `@next/next/no-before-interactive-script-outside-document`, which wants `beforeInteractive` scripts
> in `pages/_document` — a Pages Router rule. This app is App Router only (there is no `pages/`), and
> the root layout is exactly where `AdScripts`' consent-default script belongs, so the rule can only
> ever false-positive here. Turned off **with the reason written next to it**, rather than suppressed
> at the one call site, since any future one would be equally false.
>
> Wired into CI's **static** tier (`npm run lint`), so it runs on fork PRs too. `ci.yml`'s comment
> explaining why there deliberately *wasn't* a lint step is replaced by one explaining the scope of
> the lint step there now is.
>
> **Proven in both directions, not just observed green.** A throwaway probe component with a
> conditional hook, two missing deps and an `any` produced exactly four errors, one per rule; a probe
> with a needless `eslint-disable` produced the unused-directive error. The repo itself: `npm run
> lint` **clean**, `npx tsc --noEmit` **clean**.

### 0.6 Correction: §3.11's `guessDistribution` item was half-wrong when written

- **Rows created between 0007 and 0016 still hold 5 buckets.** Nothing backfilled them. They repair

  `nextDistribution[index] = (nextDistribution[index] ?? 0) + 1` extends the array —
  [recordDailyResult.ts:91-93](../lib/stats/recordDailyResult.ts#L91-L93)), and never repair
  through `migrateLocalStats` (§0.4).
- **`StatisticsSection` still falls back to a 5-element array** —
  [StatisticsSection.tsx:25](../components/settings/StatisticsSection.tsx#L25),
  `stats?.guessDistribution ?? [0, 0, 0, 0, 0]` — so a viewer whose stats haven't loaded sees five
  bars, then six. `Array(MAX_GUESSES).fill(0)` is the one-line fix and removes the last hardcoded
  copy of the number outside SQL.

Downgraded from a four-way inconsistency to a two-way one. Still LOW.

migration could leave behind. The extractor throws unless it matches exactly once, so a restructured
